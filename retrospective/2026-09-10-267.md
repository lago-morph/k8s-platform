## Part 1 — what happened

### Phase 1 — orientation and the precondition nobody had met

The owner said "get started on step 3" against a brand-new AWS account. Orientation
established that the account held only a Route53 hosted zone and that the step-3
recipe had one hard precondition: the Kyverno removal had to be on the ref the
build ran from, because it touches the management Terraform. That bead was open,
so build #6 could not legitimately start until it landed. A subagent removed the
hub install, kept all eleven audit policies dormant in git with a README recording
what each had checked, and shipped with `terraform validate` green on both modules
and the unit suite green with the Kyverno render block removed.

The interesting judgment call came immediately after. The recipe said to dispatch
base and management on `main`, but the removal could not reach `main` before the
build, because the live-evidence gate demands a live-verify pass at the pushed
commit. I resolved it by building from the branch and recording that the GitOps
paths were byte-identical between the branch commit and `main`, which made the gate
syncs legitimate clean-source syncs. That resolution held, but it was the first
appearance of a circularity that later cost an owner exception.

### Phase 2 — build #6 through the gates

The probe behaved exactly as documented: Route53 four of four, state backend
failing two because nothing was bootstrapped, which is the expected red. Base
applied in three and a half minutes, management in twenty-one. Both gates synced at
an explicit commit, the composite published its four facts, the node group reached
Ready at fifteen minutes, and the registration Secret appeared on the first
thirty-second check with the full contract. App-stack convergence matched the
documented expectation: everything healthy except the two observability rows the
storage gap explained and the workload gate that is out of sync by design.

During the long waits I ran three documentation beads in parallel subagents, each
fenced to documentation paths so they could not disturb the gated build. All three
delivered, and each one named its gaps rather than papering over them — one of them
turned up a claim in the finished-platform reference that no check attests, which
became `kp-nkz`.

### Phase 3 — spoke storage, and an exception I had to ask for

The storage diagnosis was the cleanest piece of work in the session. Read-only
against the live spoke it found two independent, both-necessary gaps: no default
StorageClass, so PVCs were created unclassed and no provisioner was ever selected,
and no EBS CSI driver, so even a correctly classed PVC had nothing to provision it.
The fix composed the addon with its IRSA role and delivered a default gp3 class,
with a red-first unit test of 49 assertions.

Then the circularity bit properly. Argo CD auto-syncs `crossplane/` and `argocd/`
from `main` with self-heal, so branch content can never be live; the gate demands
live evidence at the branch head. The gate's own comments say a composition change
demands full evidence *because* Argo will sync it to the live hub — an assumption
that is only true once the change is on `main`. I stopped and put it to the owner
rather than guessing, and they granted a one-time pass to merge and verify, on the
condition that the change be backed out immediately if it did not work.

It worked. Argo delivered it with no manual step: addon ACTIVE under the composed
role, driver registered, gp3 default, all three PVCs Bound, and both observability
Applications went from Degraded and Progressing to Healthy. Nothing was backed out.
The circularity is filed as `kp-ifh`, classed as step-6 harness work, with the
exception recorded as an exception and not a precedent.

### Phase 4 — the oracle run that found two broken checks

The first mutating oracle run came back 21 pass, 4 skip, 1 fail, and every problem
was in the tests rather than the platform. A read-only diagnosis subagent
established both with hard evidence. The Cognito federation check was skipping
because it read only the first redirect hop: the realm does broker to Cognito, but
Keycloak 24 always inserts its own `broker/<alias>/login` hop first, so the check
could never pass against a correctly configured realm — and its skip message
blamed a realm-import ordering race that the evidence ruled out. The Secrets
Manager check set an external-name annotation that is inert for that resource kind,
so the provider asked AWS for a `terraform-` prefixed name that the correctly
scoped policy denied; CloudTrail showed the AccessDenied retried through the entire
300-second window.

Both fixes shipped with unit coverage and both were validated live on the re-run,
which came back 25 pass, 0 fail — and the federation check then passed end to end,
including the federated kubectl leg. That produced the evidence for the two
readiness rows the whole build existed to settle.

### Phase 5 — recording, and the bead hygiene the owner asked for

live-verify passed at the merged commit and the fail-closed gate confirmed it. A
subagent wrote the evidence record with unusual restraint: it declined to mark
Grafana green because no HTTP check has ever been recorded for it, and it recorded
the class-then-PVC ordering as still pending because those PVCs predated the class
and bound retroactively. That refusal turned out to be exactly right, and it set up
the single most valuable measurement of the next phase.

The owner then asked whether the epic covered everything, which surfaced that five
beads filed during the session were not parented to it and that two older beads had
acceptance criteria that did not match what had been agreed. Fixing that was a
better use of ten minutes than any code change.

### Phase 6 — the first teardown this project has ever done

The owner granted four hours and asked for everything that did not need them. The
teardown was supposed to be preparation; it produced four defects, all on the
delete path that six consecutive clean builds never exercise.

IAM role deletion was impossible: the policy granted `DeleteRole` but not
`ListInstanceProfilesForRole`, which the provider calls while deleting, so all five
composed roles wedged on AccessDenied and leaked. Deleting a cluster orphans the
load balancers its in-cluster controller created, and an orphaned NLB keeps the ACM
certificate in use, which blocks the rest of the teardown — proven by contrast,
because deleting the hub's Service first had its controller remove the NLB in about
twenty seconds while the spoke's had to be cleared through the AWS API. Deleting a
composite returns in about two seconds while the cluster, database and roles are all
still live, and `kubectl get managed` does not list namespaced v2 resources, so both
obvious progress signals lie. And disabling self-heal on live Applications is
futile: my own merge mid-teardown gave Argo a new revision, bootstrap re-applied the
manifests with self-heal restored, and a new RDS instance began provisioning five
minutes after I deleted the old one.

I fixed the IAM gap in code rather than hand-deleting the roles, with a red-first
source assertion, and after the two-minute apply every wedged resource drained on
its own. That is the outcome worth remembering: fixing the cause was faster than
the workaround would have been.

### Phase 7 — build #7, driven only by the page

With the account empty, a fenced agent that could read exactly one file — the
bring-up page — executed the whole build and passed all six verification checks.
It produced nine findings, three serious, and one measurement we could not have
obtained any other way: on a cold build the gp3 class was older than all three
monitoring PVCs, which closed the ordering bead that build #6 had to leave open.

The worst finding was that the page's loudest instruction was false. Its warning
admonition and a Mermaid diagram edge both claimed that waiting for the composite
to be Ready before gate 2 deadlocks a fresh build; measured, the association and the
composite both reached Ready about six minutes before gate 2 ran, with no retry
loop. The agent's own closing comment is the part I keep: because the page spent
more design effort on that warning than on anything else, it calibrated its trust on
it, and its guesses clustered immediately afterwards.

### Phase 8 — two failures, two different answers

Build #7's oracles came back with zero skips for the first time ever, which is
itself the payoff of the hub-targeting fix, and two failures. They resolved in
opposite directions, and separating them mattered.

The federation failure was a timing window. An ACTIVE identity-provider association
does not immediately honour tokens: the kubectl leg was rejected about 01:43Z, with
the brokered login and token claims already correct at that moment, and accepted
about 01:54Z. That is the true version of the ordering concern the page got wrong.

The destination-guard failure was a false negative in the check. A 120-second
experiment showed the guard firing within twenty seconds and staying fired:
`InvalidSpecError: application destination server ... do not match any of the
allowed destinations in project 'platform-spoke'`. The check searched for "not
permitted", which is Argo's wording for a *repo* violation, so it called an
effective guard ineffective and would have said the same had the guard been deleted.
That check had never executed on any build before the skip fix unskipped it.

### Phase 9 — evidence, reconciliation, and a handoff that works

The build #7 evidence went in, rows 10 and 11 went to two clean builds, and I
reconciled two places where the tree now contradicted itself. Then, at the owner's
request, I made the next session self-sufficient: the epic carries an ordered plan
(which beads need no account, which need a live platform, which are the owner's
alone), the bring-up page carries the warning that a torn-down account is not a
fresh one, and the owner-only bead now defends itself in its first line.

One mishap in this phase, mine: I dispatched live-verify and then pushed two
documentation commits while it ran, which stranded the evidence twice over — the
gate fired before the evidence existed, and by the time it existed the head had
moved past the commit it was keyed to. Re-running at the settled head fixed it,
with the platform still barely alive.

## Part 3 — classified remedies (per the 2026-06-10 amendment and `ai/LESSONS.md` §3)

Per-rule `AGENTS-MD-*` files are no longer authored. Each remedy below is
classified in `ai/LESSONS.md` §3 order: (1) mechanical check, (2) one-line
`AGENTS.md` judgment rule, (3) structural proposal, (4) observation only. Note
that `AGENTS.md` is at its 150-line budget, so every (2) proposal costs a line
somewhere else.

### 1. Block a live-verify dispatch when the working tree or branch is ahead — class (1), mechanical

**Check design.** A PreToolUse hook in `.claude/settings.json`, matching a workflow
dispatch of `live-verify.yml`, that refuses when either `git status --porcelain` is
non-empty or `git log @{u}..HEAD` is non-empty. Message: "the evidence gate keys on
the pushed head SHA; push every content commit, docs included, before dispatching".

**Grounded in.** I dispatched live-verify at `bf520ba`, then pushed `1b94c01` and
`5ac400c` while it ran. The gate run fired at 02:06:58Z, before the evidence existed
at 02:22:21Z, and by the time evidence existed the head had moved past the commit it
was keyed to. Two independent ways to lose the same evidence, in one mistake, on a
rotating account where the window to re-run is not guaranteed. The rule already
exists in prose in `AGENTS.md` ("finalize commits before dispatching") and I broke
it anyway, which is exactly the empirical pattern §3 describes.

### 2. Assert delete-path actions on every narrowed IAM statement — class (1), mechanical

**Check design.** Extend `tests/unit/test_iam_resource_scoping.sh` with a
per-statement table of delete-path prerequisites: for each narrowed `Sid` granting
creates of a resource kind, assert the presence of the actions the provider calls
during delete, each with a comment naming the provider behaviour. The list grows by
incident; the first entry is `iam:ListInstanceProfilesForRole` on `IAMRoles`.

**Grounded in.** The policy comment recorded the narrowing as "validated on the
CREATE path before this narrowing is called done", which is true and was read as
"validated". Six clean builds passed over a policy that made every composed IAM role
undeletable. See the ADR draft `ADR-d08b24eb51` for the decision this check
implements.

### 3. A check that greps a server-generated string must pin that string in a fixture — class (1), mechanical

**Check design.** For each script under `tests/live/checks/` that matches upstream
message text, require a corresponding unit case feeding the verbatim observed
string. Enforceable as a unit lint: list the check scripts that contain a
`grep -qiE` over condition or error text, and fail when no unit test file references
that script's name. Audit-before-enforce: the destination guard now has such a
fixture; the rest must be surveyed before the lint lands green.

**Grounded in.** The destination-guard check searched for "not permitted", Argo's
*repo*-violation wording, while a destination violation is phrased "do not match any
of the allowed destinations". It reported an effective security guard as ineffective
and would have reported the same had the guard been deleted — the dangerous
direction. It had never executed on any build.

### 4. Diagnostic tools are tested on content, not exit status — class (2), one `AGENTS.md` line

**Proposed line.** "A diagnostic's test asserts on what it printed, never on its
exit status: the failure mode of a read-the-live-object tool is to read the wrong
field and report nothing, successfully."

**Grounded in.** `scripts/crossplane-trace.sh` reads `.spec.resourceRefs`; v2
composites keep them under `spec.crossplane.resourceRefs`. On a live composite with
sixteen refs it printed the conditions, then END TRACE, and exited 0. A June note in
the archived register had recorded this exact bug as diagnosed and fixed. `AGENTS.md`
already names this script as *the* tool for a stuck composite, so the one tool you
reach for is silent precisely when you need it (`kp-2al.28`).

**Budget note.** If this line is adopted, the cheapest swap is to fold it into the
existing "Domain loops" bullet that already names the script, rather than adding a
new standalone line.

### 5. Never merge to `main` during a teardown — class (1) if scripted, else documentation

**Where it belongs.** In the teardown runbook (`kp-2al.30`), not in `AGENTS.md`. If
the teardown becomes a script, it can assert at entry that no merge has landed since
it started, which makes it class (1). As prose in the operating agreement it is a
single-context rule that would consume budget for a situation that arises once per
teardown.

**Grounded in.** Merging PR #266 mid-teardown gave Argo CD a new target revision;
bootstrap re-applied the Application manifests from git with self-heal restored, and
a brand-new RDS instance began provisioning five minutes after I deleted the
XDatabase. Patching self-heal off on live Applications is futile against a revision
change.

### 6. Wait on managed resources, never on the composite, when deleting — class (1), mechanical

**Check design.** Part of the same teardown script: the completeness check asserts
zero EKS clusters, zero load balancers, zero RDS instances and no `k8-platform-*`
IAM roles, and the script waits on the namespaced managed-resource kinds rather than
the composite. The check is what makes the ordering self-enforcing rather than
remembered.

**Grounded in.** `kubectl delete xdatabase` plus `kubectl wait --for=delete` both
returned in about two seconds while the RDS instance, spoke EKS cluster, node group,
certificate and five IAM roles were still live. `kubectl get managed` showed two
unrelated leftovers and nothing else, which read as reassuring.

### 7. An account reset is not an account provisioning — class (4) → now documented

**Disposition.** Already discharged as documentation rather than a rule: the
bring-up page's step 1 now carries the warning, the owner-only bead carries it, and
the teardown bead carries it. No further remedy proposed.

**Grounded in.** The Terraform state bucket and DynamoDB lock table are bootstrapped
outside Terraform and survive `action=destroy`, so build #7's probe came back green
where the page predicts red. Left undocumented, this produces a false finding on the
owner's own run.

### 8. "Fixed" in a historical note is a hypothesis — class (4), observation

**Disposition.** Observation only; no rule proposed. A rule saying "distrust the
record" is unactionable prose of exactly the kind §3 item 4 warns against. The
actionable version is already covered by item 3 and by the existing done-contract:
claims need evidence, and the fix for a silent-read bug needs a content assertion.

**Grounded in.** The 2026-06-12 entry describing the `resourceRefs` jsonpath bug
recorded a catch-block fix as landed. The bug was still in the source at two places
on 2026-09-10, and only a provisioned composite could show it.

## The one-sentence version

Five of this session's defects were invisible to six consecutive clean builds, and
every one of them surfaced by doing something the platform had never done — deleting
instead of creating, running a check that had only ever skipped, pointing a
diagnostic at a real object, and handing the documentation to a reader who had
nothing else to read.
