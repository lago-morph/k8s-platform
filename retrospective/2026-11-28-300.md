## Part 1 — what happened

### Phase 1 — Following the handoff's Part 3, steps 3.0 to 3.6

The goal was to run the handoff's migration procedure exactly, stopping
on any unexpected result. Steps 3.0 (sandbox and baseline checks), 3.1
(1.2.2 backup on a copy, with the GitHub Dolt remote stripped first) and
3.3–3.6 went as written. Two documented "not verified" items came up. The
clone of the empty DoltHub database failed, and the handoff's fallback
(let init create the database, add the remote after the restore) worked.
`origin` did not survive the restore, which was moot because none
existed. One finding was cosmetic: 1.2.2 `backup status` printed
"Database size: 0 B" for a 19 MB backup. The bead-by-bead comparison
(5 commands × 175 beads × 2 binaries, run in parallel) matched everything
except a new `revision` field. The owner stated mid-step that the R2
comparison was not needed, because this session had no R2 credentials.

### Phase 2 — Step 3.7 broke twice

**First break, my own bug.** I had started the server with
`cd $M && nohup dolt sql-server … &`. That backgrounds a subshell, so
the PID file held the subshell's PID and the kill never reached dolt. The
same Bash call then deleted the data directory, cloned again, started a
second server (which died: "Port 3307 already in use") and ran the check
queries. Those queries answered from the **old** server, which still had
the deleted files open, so they returned correct-looking counts. The
`pgrep` output in the same call showed the old server alive. I stopped
and reported it, and the owner had me redo step 3.7 from a clean state.

**Second break, a real design defect.** A plain `dolt clone` of the
pushed database could not be opened by bd 1.3.4:
`table not found: leases`. bd's machine-local tables are listed in
`dolt_ignore`, so they never reach DoltHub. Restarting the server (the
owner's first suggestion) did not help. The owner then proposed cloning
*with bd*. `bd bootstrap --yes`, run against an empty server with
`sync.remote` set, cloned through the server and created the tables.
Compare #2 then matched. This changed Part 5 of the handoff: the design
used `dolt clone` for every new session and would have produced an
unreadable graph in every fresh container. My suggested next step had
been a research pass; the owner's direct suggestion was faster and
correct.

### Phase 3 — Part 5 as one PR (#300)

The owner approved, said yes to both open points (keep a pre-push sync,
record the outcome in the handoff), and asked for an onboarding seed
document for other repositories. I wrote `scripts/beads-server.sh` (detect,
install, creds, start, sync-loop, sync-now, status, setup), rewired the
hooks and settings, and replaced the `.beads/` files with the migrated
workspace's. Two things went beyond the handoff's design:

- **The beads block in `session-start.sh` now runs before the hook's
  remote-only early exit.** As designed, `detect` would never have run on
  a local or shared machine.
- **The status line and the pre-push guard now check the bd version
  first.** This session still had bd 1.2.2 installed. Once
  `metadata.json` said server mode, a 1.2.2 `bd status` would have
  connected to the migration server holding the v66 database.

The test (37 checks, all external commands stubbed) found two script bugs
before CI did:

- the foreign-process report decided on `ps` output, so a PID that `ps`
  could not describe was silently treated as no process;
- the status test did not reset its log between cases.

A read-only live `detect` correctly refused to set up because of the
migration's own server. I also put the `git rm` deletions in the wrong
commit (they had been staged before I split the commits) and rebuilt the
three commits before pushing. CI was green; the owner asked me to merge,
and I used a merge commit to keep the three commits.

## Part 3 — remedy proposals (classified per `ai/LESSONS.md` §3)

Beads were **unavailable in this session**: bd 1.2.2 was installed, the
repo was in server mode, and the only server was the migration's. So no
bead IDs could be recorded, which `ai/LESSONS.md` L44 requires. Rows
marked "bead owed" need a bead in the first session after #300.

1. **(a) — adopted (#300).** *A plain `dolt clone` gives a database bd
   cannot open.* `test_beads_server.sh` asserts `start` calls `bd
   bootstrap` and never `dolt clone`. The beads skill's recovery drill and
   `ai/beads-dolthub.md` say why. Grounded in compare #2's
   `table not found: leases`.
2. **(a) — adopted (#300).** *The PID from `cd x && nohup … &` is the
   subshell's.* The test asserts `server.pid` names the server process
   itself. Grounded in the first 3.7 stop that never reached the server.
3. **(b) — proposed, needs an `AGENTS.md` line swap (file is at 150).**
   *In one Bash call, a verification printed the failure and the
   destructive steps ran anyway.* Proposed line: "In a Bash call, a check
   that guards a later destructive step must abort the call when it fails
   (`|| exit`), never print and continue." Mechanising it was considered:
   a hook cannot tell which echo is a guard. The cost here was small only
   because the database was already on DoltHub.
4. **(d) — observation.** *A data-collection script that discards stderr
   can turn a hard failure into an empty result.* My collector used
   `2>/dev/null`; the first compare #2 collected 0 beads and was caught
   only because the comparator crashed on the empty file. These are
   one-off scripts, so the habit is to check the record count before
   comparing. No rule.
5. **(d) — observation.** *Splitting staged work into commits.* `git rm`
   stages immediately, so a later path-limited `git add` plus commit
   swept it into the wrong commit. I caught it with `git show --stat`
   before the push. Habit: `git diff --cached --stat` before each commit.
6. **(a) — adopted (#300).** *A new-mode config and an old-mode binary in
   the same session.* `status` refuses to query with a bd that is not the
   pin (tested), and the pre-push guard goes through `status`.
7. **(c) — open, bead owed.** *Background-process survival.* Claude Code
   does not document whether `nohup` processes started by SessionStart
   survive across turns. The first session after #300 must confirm that
   the server and the loop are alive several turns in (handoff 5.3).
8. **(c) — open, bead owed.** *Shared-sandbox path untested live.* The
   format of `beads-sync.state` is unknown to this repo, so `status`
   prints its last line verbatim. This needs one session on the shared
   sandbox, plus the owner's description of the file format.
9. **(d) — environment fact, for `ai/environment.md`.** *Creating a PR
   through the GitHub MCP tool subscribes the session to that PR's
   events* without a `subscribe_pr_activity` call. The events are
   webhook-driven, not timed wakeups, so they are consistent with L45.
   It is worth recording so a future session does not think it broke
   the no-polling rule.
10. **(d) — observation.** *`dolt send-metrics` ran next to the server*
    although `metrics.disabled true` had been set in the same
    `DOLT_ROOT_PATH`. Unexplained. `detect` treats the server's
    descendants as its own, so it does no harm.
11. **(d) — observation, worked well.** *Stopping on each unexpected
    result.* All three stops were the right call. The owner's answers
    (skip R2; redo 3.7 from clean; clone with bd) each took one turn,
    against what an improvised fix would have cost.
