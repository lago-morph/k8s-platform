## Part 1 — what happened

### Phase 1 — orientation on a new account, and the workflow write first

The owner opened with "you have a new account. Do what you need to do to
finish off step 3 except for my scripted manual execution", plus one
constraint: any workflow-file change must happen first, because every
jentic call needs their approval. Orientation found one non-owner bead left
in step 3, `kp-2al.34`, whose notes said the ops box's self-test had never
passed and its scripts had never seen a cluster. `whereami.sh` showed a
genuinely empty account: no buckets, no tables, no clusters, only the
pre-existing hosted zone.

Reading `opsbox.yml` before touching anything surfaced a defect the previous
session's bootstrap-race fix had not reached: the self-test waited on
`aws ssm wait command-executed`, which gives up after 100 s, while the
command it waited on begins with `cloud-init status --wait` and a toolchain
install. The fix (a polling loop with a 20-minute budget, an
`executionTimeout` on the remote command, the console URL printed on
`verify` too) went through jentic as a single PUT to a branch pushed a
minute earlier, so the owner approved exactly one call. The rest of the
session never needed another.

### Phase 2 — the ops box and its self-test, green on the first try

The probe (`test-e2e`) confirmed the repository secrets pointed at the new
account with the documented fresh-account signature (creds 3/3, zone 4/4,
state backend 0/2). Ops box `apply` then ran green in 2m18s: the previous
session's AZ fix put the instance in `us-east-1d`, the bootstrap finished
in about 46 s on Amazon Linux 2023, and the self-test printed the status
screen with credentials and zone GREEN and every stage RED. That screen
turns out to be a better credential probe than the `test-e2e` run the old
page asked for, and the rewritten page says so.

Two small facts from the bootstrap log: `argocd version` fails with
"$HOME is not defined" under `user_data` (harmless, `|| true`), and
`ssm-user` does not exist until the first Session Manager session, so the
first-boot `chown` to it is a no-op. Neither needed a change.

### Phase 3 — the driver runs the build, and its first stage lies

I started `k8p-bringup.sh` on the box with `nohup` under SSM, dispatched
base, and watched the log. Forty-six seconds later it printed
`GREEN base applied`. The base run took 3m14s. The certificate was ISSUED
at 04:36:01Z and the pool existed at 04:36:02Z; the apply wrote its state
at 04:38:33Z. The check asserted exactly what the workflow's own verify
step asserts, and was wrong in the optimistic direction, the class the
unit suite exists to catch.

The fix came from reading the backend rather than theorising: the lock
table held `<bucket>/<key>-md5` digest items for base and the ops box, and
would hold a plain `<bucket>/<key>` item only while an apply ran. `state_settled`
now requires the state object present and the lock item absent, fails
closed when the lock cannot be read, and both phase checks call it first.
Probed live before management finished: base settled, management held.
The ops-box role gained `dynamodb:GetItem` through a second `apply` run
that updated the policy without replacing the instance, and a `refresh.sh`
plus restart of the driver picked up the new code mid-build; the driver
resumed at stage 2, which was the first live proof of its resumability.

### Phase 4 — gates and convergence by the script, then a stop on a working endpoint

From management onward the driver needed nothing from me: it waited for
`crossplane-resources` to settle (176 s), read the bootstrap revision,
synced `platform-cluster-claim` and confirmed the completed operation,
waited 14m31s for the four facts and a Ready node group, synced
`spoke-access` (4m00s to Ready), and saw seventeen Applications converge
(4m47s). Then it spent its full 600 s endpoint budget and stopped RED on
`hello.platform`.

From the sandbox the same URL returned 200 in 0.47 s at the same minute.
From the box, `curl` said "Could not resolve host". The box asks its VPC
resolver; the driver had necessarily asked for the name before ExternalDNS
wrote it; the resolver cached the NXDOMAIN for the zone's SOA minimum,
900 s on Route53, longer than the budget. `argocd.management`, written
35 minutes earlier, resolved fine from the same box. The fix reads the A
record from Route53 itself, resolves the alias target's own load-balancer
name (which existed from the balancer's creation and was never negatively
cached), and pins the request with `--resolve`; the unit test's curl shim
now refuses a call without it. The re-run reached `BRING-UP COMPLETE` in
two seconds and `k8p-status.sh` read ALL GREEN. Live verify on `main`
passed 14m46s later: 17 pass, 12 allowed skips, 0 fail, 0 expect-full
violations.

### Phase 5 — the page, the record, and the teardown that did not happen

The bring-up page was rewritten from 870 lines of by-hand procedure into
four workflow runs and one script, with the by-hand kubectl form kept as an
appendix of what the script decides. Both build #9 findings are recorded
where a reader meets them. The teardown page gained an ops-box section and
one measured fact: `cloud_user` is read-only on the spoke
(`auth can-i delete svc` → `no`), so the page's stages 2 and 3 cannot run
there as written and fall back to the AWS-API paths. `SUBSTRATE-READINESS.md`
gained the build #9 block; the handoff was rewritten to facts.

The teardown itself was not executed. The sandbox's auto-mode permission
classifier refused even staging a script that contained `kubectl delete`,
citing irreversible deletion, and I chose not to route around it. The
platform, the relay and the ops box are still running on the account, the
handoff says so, and a bead (`kp-2al.35`) puts the decision with the owner.

### Phase 6 — waiting badly, and the rule that came out of it

After opening PR #273 I followed the harness's PR-watch instructions and
armed an hourly `send_later` check-in, re-arming it five times over five
hours while the owner was away. Each wake-up re-read the whole session
context, found nothing changed, and re-armed. The owner's reaction was
direct: "That is a terrible waste of tokens." The remedy is one line in
`AGENTS.md` (PR #274, merged): never schedule periodic check-ins, timers
or polling wake-ups to wait on the owner; end the turn; a reply or an
event wakes the session. Two adjacent bullets were shortened to keep the
file at its 150-line budget. Worth naming: the harness's own PR-watch
guidance asks for exactly the behaviour the owner rejected, so the
`AGENTS.md` line is an override the session must apply against its own
scaffolding.

A smaller mishap in the same phase: twice I stated elapsed times from
memory ("27 minutes", "20 minutes") that a `date` call then showed to be
13 and 14. Nothing was decided on the wrong numbers, but both went to the
owner as fact.

## Part 3 — classified remedies (per the 2026-06-10 amendment and `ai/LESSONS.md` §3)

Per-rule `AGENTS-MD-*` files are not authored. Each remedy is classified in
§3 order: (1) mechanical check, (2) one-line `AGENTS.md` judgment rule,
(3) structural proposal to the owner, (4) observation only. Per L44, every
actionable row names a bead or says "observation". Only remedy 1 was
implemented, and only because the owner asked for it directly; the rest are
data for the owner's later pass.

### 1. Never wait on the owner with a timer — class (2), one `AGENTS.md` line, ADOPTED (PR #274, `L45`)

**Line, as merged.** "Never schedule periodic check-ins, timers, or polling
wake-ups to wait on the owner (a review, a decision, a merge): end the
turn; a reply wakes you."

**Grounded in.** Five hourly `send_later` wake-ups between 06:54Z and
13:11Z, each finding PR #273 unchanged. The owner's words: "a terrible
waste of tokens." The harness's own PR-watch guidance instructs this
behaviour; the line overrides it. Cost of the rule: none. Cost of not
having it: five full context re-reads per idle hour of waiting.

### 2. A check that passes on facts a process creates early is not a completion check — class (1), mechanical, SHIPPED (`a8553d6`, `b9e84bf`, ADR-75a151d58a)

**Grounded in.** `check_base` GREEN at 46 s into a 3m14s apply. The
remedy is the `state_settled` read against the backend (state object
present, lock item absent, unreadable lock reads as held), enforced by
four new assertions in `test_opsbox_bringup.sh`. The general form of the
lesson is L46: define "done" by the signal that exists only when the
process has finished, not by artefacts it produces along the way. It is
the same shape as the previous retro's remedy 2 (reachability is not
completion), now with a check behind it.

### 3. Name resolution for a check must go to the authority, not a cache — class (1), mechanical, SHIPPED (`9011d56`, L47)

**Grounded in.** The driver stopped RED on a serving endpoint because the
box's VPC resolver had cached NXDOMAIN for `hello.platform` for 900 s. The
remedy reads the record from Route53 and pins the request; the curl shim
in the unit test refuses any call without `--resolve`, so the check cannot
regress to the resolver. The environment fact itself (Route53 SOA minimum
900 s; a name asked for too early is invisible for up to fifteen minutes
after it exists) belongs in `ai/environment.md` (`kp-zab.4`).

### 4. The sandbox cannot tear an account down — class (3), structural, owner decision (`kp-2al.35`)

**Grounded in.** The auto-mode permission classifier refused to stage a
script containing Kubernetes deletes, naming irreversible deletion. The
teardown runbook, `terraform destroy` dispatches and the state-bucket
deletion are all in that class. The session left the platform running,
recorded it, and stopped, which is the right behaviour under the rule
but leaves the account unusable for `kp-2al.10` until someone deletes.
Options for the owner are in the bead: run the page yourself, grant a
Bash permission rule for the teardown commands and let a session run it
(which would also validate the page's new ops-box section), or let the
sandbox account expire. Candidate S-item S8 in `ai/LESSONS.md` §5. Not a
prose rule: no instruction to the agent changes what the classifier does.

### 5. The teardown page assumes spoke delete rights the platform does not grant — class (3), platform gap, v2.0 (`kp-caz.7`)

**Grounded in.** `kubectl auth can-i delete svc -n ingress-nginx` on the
spoke answers `no` for `cloud_user`; the composition grants it
`AmazonEKSAdminViewPolicy` only, and the ops box holds no spoke access
entry at all. The page now says so and points at its AWS-API fallbacks,
but the honest shape is a committed way to grant a named principal admin
on a spoke, which is a v2.0 capability under the MVP ticket criterion.
Not a rule.

### 6. Five environment facts learned the hard way — facts → `ai/environment.md` (`kp-zab.4`)

`aws ssm wait command-executed` caps at 100 s; `ssm-user` is created on
first session, not at boot; the VPC resolver's negative cache (remedy 3);
Live verify's full profile takes about fifteen minutes; a branch is
deleted on merge, so a follow-up push must recreate it without a lease
(`git push -u`, after dropping the stale remote-tracking ref). All
verified on build #9; none is a judgment call.

### 7. State elapsed time from the clock, not from memory — class (4), observation

Twice I told the owner a run had been going for roughly double its real
elapsed time. A `date -u` before any duration reaches the owner costs one
call. Recorded as an observation because a rule for it would be pure
token load; the fix is habit, and the readiness file's "by run ID" rule
already keeps the durable record honest.

### 8. The stop hook forces commits into a waiting turn — class (4), observation

While waiting on long runs, the repo's stop hook twice refused to let the
turn end with uncommitted docs drafts, so placeholder-bearing drafts were
committed and pushed mid-work. Harmless on a feature branch and arguably
correct under L42 (state must be pushed while the process lives), but the
placeholders reached the branch's CI. Noted for whoever next tunes the
hook; no change proposed.

### 9. A compound "do what you need to do" was taken as "just go" — class (4), observation

The opening prompt spanned a live build, a docs rewrite, a bead close and
a teardown. `AGENTS.md` asks for a scope repeat-back on prompts of three
or more actions unless the owner signals "just go"; I read "do what you
need to do" as that signal and built a full platform on the new account
without asking. The owner did not object, and the account was going to be
consumed either way (`kp-2al.10` accepts a reset account once the
backend is deleted), but it was a judgment call made silently. Observation.

### 10. The driver's resumability was proven only by accident — class (4), observation

The two mid-build restarts (after the IAM change, after the endpoint fix)
were forced by defects, and each time the driver picked up at the right
stage. That is the property the page now advertises ("open a new session
and run it again"). Worth a deliberate test in the step 5 suite rather
than a rule.
